# 경계면 중심 QA

구현용 하네스를 만들거나 모듈 통합을 검증할 때 읽는다. 원본 하네스의 핵심 교훈은 생산자와 소비자를 함께 비교하는 것이다. 개별 파일이 존재하고 빌드가 성공해도 연결이 잘못되면 실제 동작은 실패할 수 있다.

## 리뷰와 실행 QA 구분

`harness_reviewer`는 읽기 전용으로 결함을 분석해 메인에게 반환한다. `harness_qa`는 실제 명령을 실행하고 캐시·로그·테스트 산출물을 만들 수 있는 `workspace-write` 역할이다. sandbox는 실제 허용 범위를 따르며 역할명만으로 능력을 판단하지 않는다.

QA는 제품 코드를 수정하지 않는다. 작은 수정도 메인이 지정한 워커가 담당하고 QA가 재검증한다. QA의 쓰기 범위는 배정된 테스트·검증 산출물과 통신 도구를 통한 사건 기록이며, 제품 수정 책임과 섞지 않는다.

## 경계면 비교표

| 생산자 | 소비자 | 확인할 불일치 |
| --- | --- | --- |
| API의 실제 JSON 응답 | 클라이언트 파서·훅·화면 | 배열/객체 래핑, 필드명, null, 타입 변환 |
| DB 컬럼·조회 결과 | API 직렬화와 프론트 타입 | snake_case/camelCase, 날짜·금액·ID 표현 |
| 실제 라우트 구조 | 링크·리다이렉트·라우터 호출 | 접두사, 동적 파라미터, 경로 그룹 |
| 상태 전이 정의 | 상태 업데이트 코드와 UI 분기 | 누락된 종료 전이, 도달 불가능 상태 |
| HTTP 요청 수락 응답 | 폴링·콜백·최종 결과 처리 | 202 응답에서 완료 데이터 접근 |
| 에이전트 결과 | 다음 작업의 입력 계약 | 경로·필드 누락, 실패 결과를 성공으로 소비 |
| 생성된 에이전트·스킬 | 오케스트레이터와 포인터 | 역할명·경로 drift, 존재하지 않는 도구 가정 |

예를 들어 `fetchJson<Profile[]>()`라는 제네릭 선언만으로 API의 `{ profiles: [] }` 응답이 배열로 바뀌지 않는다. 응답을 만드는 코드와 사용하는 코드를 함께 읽고 필요하면 실제 응답을 관찰한다.

## 검증 절차

1. 변경된 모듈의 입력·출력과 의존 소비자를 나열한다. 전체 시스템을 무작정 훑기보다 변경 경계와 회귀 위험을 먼저 확인한다.
2. 양쪽 코드를 함께 읽어 데이터 형식과 오류 동작을 비교한다. 문서의 선언과 실제 동작이 다르면 실제 증거를 우선한다.
3. 관련 테스트 명령과 부작용을 확인한다. 캐시·출력·테스트 데이터베이스가 다른 실행과 충돌하면 메인에게 순차 실행 또는 격리를 요청한다.
4. 정상 입력, 빈 값·누락·오류·비동기 완료 등 의미 있는 경계 사례를 실행한다. 설치·타입 검사·빌드·기능 테스트의 범위를 각각 구분한다.
5. 실패를 발견하면 재현 절차, 기대/실제 동작, 파일·행, 영향받는 생산자와 소비자를 반환한다.
6. 수정된 구간과 그 소비자를 재검증한다. 무관한 전체 테스트를 반복하지 않되 공용 계약 변경은 영향 범위를 넓힌다.

## 점진적인 QA 배치

```text
공통 계약 확정
  ├─ 모듈 A 구현 → A와 소비자의 경계면 QA
  └─ 모듈 B 구현 → B와 소비자의 경계면 QA
메인 통합 → 교차 모듈 검사 → 최종 결과
```

소비자가 아직 없으면 계약 검토만 수행하고 실제 통합 검사는 `not_run`으로 남긴다. 구현 중인 파일을 보고 잠정 결함을 단정하지 말고 메인이 확정한 완료 구간을 기준으로 평가한다. 최종 통합 전 점진적인 검사가 있더라도 마지막 통합 검증은 필요하다.

## 웹 앱 검사 예

- API 목록과 실제 클라이언트 호출을 대응시킨다. 호출이 없는 API는 관리자용·외부용 등 의도된 용도인지 확인한 후 누락 여부를 판단한다.
- 응답 래핑, 필드 이름, 선택 필드, `null` 처리, 동기·비동기 응답을 비교한다.
- 라우트 그룹처럼 URL에 나타나지 않는 디렉토리와 동적 세그먼트를 고려해 링크를 확인한다.
- 상태 맵의 허용 전이와 실제 업데이트를 대조한다. 자동으로 실행되지 않는 전이가 수동·외부 이벤트 용도인지 확인한다.
- 중간 상태에서 완료·실패 상태로 빠져나오는 경로가 있고 UI가 그 상태를 처리하는지 확인한다.

## 하네스 검사 예

- 실행 중인 워커들의 수정 경로와 공유 빌드 출력이 겹치지 않는다.
- 자식이 메인의 `plan.json`이나 공용 설정을 수정하지 않는다.
- 선행 작업 실패 시 필수 소비자를 완료 처리하지 않는다.
- 읽기 전용 역할은 결과 메시지를 반환하고 메인이 파일로 기록한다.
- 부분 재실행에서 공용 계약의 소비자가 다시 검증되고 과거 기록이 보존된다.
- 도구 목록에 없는 API를 가정하거나 결과 수집 없이 완료를 보고하지 않는다.

## 보고 형식

검사마다 상태를 `passed`, `failed`, `not_run`으로 표시한다. 결함에는 영향·재현·근거·권장 수정 범위를 포함하고 확인하지 못한 영역에는 사유를 붙인다. 기계 판독용 결과는 [오케스트레이터의 결과 계약](orchestrator-template.md)을 따른다.

예: “failed — API가 `{ profiles: [] }`를 반환하지만 훅은 `.map()`을 직접 호출한다. 생산자 `src/api/profiles.ts`, 소비자 `src/hooks/useProfiles.ts`를 비교했으며 목록 요청 시 TypeError가 재현됐다.” 실제 확인한 경우에만 이와 같이 단정한다.

읽기 전용 검토에서 문제를 찾지 못했다면 “검토 범위에서 발견 없음”으로 보고한다. 실행하지 않은 화면·브라우저 검사를 통과로 바꾸지 않는다. 기본 2회의 수정·재검증 후에도 필수 실패가 남으면 메인에게 실패로 반환한다.

## 협업과 완료 근거

결함을 찾으면 담당 워커에게 재현·기대 결과·실제 결과·근거를 먼저 전달하고 메인에게도 알린다. 불명확한 계약은 관련 동료에게 구체적으로 질문하되 메인이 확정하기 전에는 계약을 바꾸지 않는다. 수정 준비 또는 검증 완료 시 인계한다. 중요한 발신은 기록 후 실제 메시지 도구로 보내고 답변·수신 확인을 연결한다. 읽기 전용 리뷰어의 기록은 메인이 담당한다. 세부 절차는 [실행 가이드](runtime-guide.md)를 따른다.

필수 검사의 실패와 미실행은 완료를 막는다. 결과에는 run/task ID, 실제 산출물, 검사별 required·상태·근거를 적고 메인이 결과 등록과 최신성 검증을 수행한다.
