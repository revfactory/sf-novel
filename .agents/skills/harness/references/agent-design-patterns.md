# Codex 에이전트 설계 패턴

Phase 2·3에서 역할 분리, 실행 순서, 커스텀 에이전트 형식을 정할 때 읽는다.

## 실행 구조

메인 세션이 작업 그래프와 통합을 담당하고 필요한 서브에이전트를 호출한다. 독립 작업에 병렬 실행을 사용하고, 결과에 의존하는 작업은 선행 결과를 받은 뒤 실행한다. 공동 파일 시스템은 협업을 가능하게 하지만 자동 병합이나 충돌 방지를 보장하지 않는다.

도구 이름은 런타임별로 다르다. 예를 들어 어떤 CLI에는 `spawn_agent`, `send_input`, `wait`, `close_agent`가 있고, 다른 환경에는 `collaboration.spawn_agent`, `followup_task`, `send_message`, `wait_agent`, `interrupt_agent`가 있다. **현재 노출된 스키마를 확인한 뒤 호출한다.** 종료·중단·추가 작업의 의미가 서로 같다고 가정하지 않는다. `interrupt_agent`는 작업 중단이지 세션 종료의 대체 명령이 아니다.

Codex는 기본적으로 서브에이전트를 지원한다. 프로젝트에서 설정이 필요하면 현재 버전의 공식 스키마와 로컬 설정을 확인한다. 검증한 설정명은 `[agents]` 아래 `enabled`, `max_concurrent_threads_per_session`이다. 동시 실행 한도가 높아도 쓸모 있는 작업만 실행한다. 이 스킬은 사용자의 전역 설정을 수정하지 않는다.

## 여섯 팀 패턴

| 패턴 | 작업 그래프와 사용 시점 | Codex 실행 방식 |
| --- | --- | --- |
| 파이프라인 | 분석 → 설계 → 구현 → 검증. 순차 의존성이 강한 작업 | 메인이 선행 결과를 확인하고 다음 역할을 호출한다. 단계 안의 독립 작업만 병렬화한다. |
| 팬아웃/팬인 | 공통 입력 → 독립 조사·구현 → 통합 | 범위가 다른 자식 2~3개에 나누고 메인은 공통 계약과 통합을 맡는다. |
| 전문가 풀 | 입력에 따라 보안·성능·데이터 등 선택 | 반복 역할은 커스텀 에이전트로 보관하되 필요한 역할만 실행한다. |
| 생성-검증 | 생성 → 리뷰/QA → 수정 → 재검증 | 생성자와 검증자의 책임을 분리한다. 수정 루프는 기본 2회까지이며 실패를 강제 통과시키지 않는다. |
| 감독자 | 실행 중 새 작업이 발견되는 가변 작업량 | 메인이 작업 장부를 갱신하고 빈 슬롯에 다음 작업을 배정한다. 워커는 추가 작업을 제안할 수 있다. |
| 계층적 위임 | 도메인 → 모듈 → 세부 작업 | 논리 구조는 계층적으로 설계하고 실제 호출은 메인이 평탄화한다. 자식은 기본적으로 추가 에이전트를 만들지 않는다. |

예: 분석은 파이프라인, 모듈 구현은 팬아웃, 검증은 생성-검증으로 조합한다. 서로 의존하는 세계관·인물·플롯을 처음부터 완전 독립 작업으로 가정하지 않는다. 먼저 공통 설정을 확정하거나 초안 탐색 후 동기화하는 단계를 둔다.

## 분리와 재사용

| 판단 축 | 분리할 이유 | 함께 수행할 이유 |
| --- | --- | --- |
| 전문성 | 지식·검증 관점이 다름 | 책임과 판단 기준이 거의 같음 |
| 병렬성 | 입력이 준비되었고 수정 경로가 독립적임 | 같은 파일·공용 계약을 함께 바꿔야 함 |
| 컨텍스트 | 독립 탐색 결과를 요약하면 부담이 줄어듦 | 전달할 맥락이 실행 작업보다 큼 |
| 재사용성 | 여러 실행에 반복되는 안정적인 역할 | 이번 실행의 짧은 일회성 질문임 |

기존 역할이 요구를 포함하면 재사용한다. 일부 확장은 기존 호출부를 확인하고 일반화한다. 의도적인 전문성이 다를 때만 새 역할을 둔다. 에이전트마다 스킬을 하나씩 복제할 필요는 없으며 여러 역할이 같은 절차를 참조할 수 있다.

## 기본 역할

| 역할 | 책임 | 기본 쓰기 범위 |
| --- | --- | --- |
| `harness_explorer` | 좁은 코드 질문과 영향 경로 조사 | 읽기 전용, 결과는 메시지로 반환 |
| `harness_architect` | 계약·의존성·분할 설계 제안 | 읽기 전용, 메인이 설계를 기록 |
| `harness_worker` | 배정된 파일 구현 | 소유한 파일과 자기 작업 산출물 |
| `harness_reviewer` | 결함과 회귀 위험 독립 검토 | 읽기 전용, 메인이 리뷰를 기록 |
| `harness_qa` | 명령 실행과 경계면 검증 | 허용된 캐시·로그·자기 작업 산출물 |

정의 파일이 있다고 현재 세션에서 즉시 선택 가능한 것은 아니다. 노출된 역할 목록을 확인한다. 새 역할을 현재 런타임이 아직 발견하지 못한 경우 해당 정의를 읽어 빌트인 역할의 작업 지시에 전달하고 그 사실을 기록할 수 있다. 선언되지 않은 `agent_type`을 임의로 호출하지 않는다.

## 커스텀 에이전트 TOML

프로젝트의 `.codex/agents/domain_worker.toml` 예시다. 모델을 생략하여 부모 모델과 추론 수준을 상속한다.

```toml
name = "domain_worker"
description = "도메인 변환 규칙을 배정된 파일에 구현한다."
sandbox_mode = "workspace-write"
developer_instructions = """
메인이 제공한 목표, 입력, 선행 결과, 파일 소유권, 완료 기준을 확인한다.
당신은 혼자 작업하지 않는다. 다른 작업자의 변경을 되돌리지 말고 현재 코드에 맞춰 수정한다.
명시적으로 소유한 파일만 수정한다. 공용 계약 변경은 메인에게 제안하고 확정된 결과를 기다린다.
plan.json, AGENTS.md, 공용 설정, 다른 작업자의 파일은 메인이 관리한다.
추가 분할이 필요하면 메인에게 제안한다. 기본적으로 자식 에이전트를 생성하지 않는다.
재호출 시 갱신된 input.md, 입력 지문, 결정, 스킬, 이전 산출물과 피드백을 읽는다.
다른 작업에 영향을 주는 발견은 먼저 알리고 동료에게 구체적으로 질문하며 신속히 답한다.
중요 메시지는 기록 후 실제 도구로 전달하고, 읽기 전용 역할의 기록은 메인에게 요청한다.
완료 시 상태, 변경 경로, 실제 실행한 검사와 근거, 남은 문제를 반환한다.
필수 입력 누락이나 실패는 숨기지 않고 메인에게 보고한다.
"""
```

이 파일은 Markdown 역할 설명의 확장자가 바뀐 것이 아니라 Codex의 독립 TOML 정의다. 필수 필드 `name`, `description`, `developer_instructions`를 사용한다. 별도 설정의 역할 등록 테이블이나 지원 여부가 불명확한 필드를 추가하지 않는다.

## 협업 계약

- 메인은 작업 장부의 유일한 작성자다. 작업자에게 태스크를 자율 claim하도록 지시하지 않는다.
- 쓰기 경로는 파일 또는 분명한 하위 디렉토리로 배정한다. 상위 디렉토리를 소유한 작업과 그 하위 파일 작업은 동시에 실행하지 않는다.
- 공용 타입·설정·lockfile·`AGENTS.md`는 메인이 통합한다. 워커가 필요성을 발견하면 제안과 영향 범위를 보낸다.
- 탐색·리뷰는 읽기 전용이어도 쉘 실행이 가능할 수 있다. 파일 생성이 필요한 테스트 실행과 읽기 전용 검토를 구분하고 실제 sandbox를 따른다.
- 같은 주제는 기존 에이전트에 갱신된 패킷·결정·스킬 경로를 보내 맥락을 재사용한다. 독립 작업은 작은 완결된 패킷을 전달한다. 독립 리뷰에는 지원될 때 새 컨텍스트를 사용한다. 전체 대화 상속·특정 fork 옵션을 가정하지 않는다.
- 실제 자식 ID와 활동 상태를 작업 상태와 구분한다. 결과 등록 후에도 유휴·중단 응답을 확인하고, 확인 전에는 쓰기 소유권을 넘기지 않는다. 단순 메시지·기다림·장부 변경은 재개·중단·슬롯 반환을 보장하지 않는다.
- 자식에게 동료의 실제 ID·역할·담당 경계를 알려준다. 발견·질문·답변·계약 제안·차단·입력 준비·인계를 적극적으로 전한다. 동료가 토론할 수 있어도 메인만 소유권과 계약을 바꾼다.
- 중요한 통신은 `_workspace/communications/<run-id>.jsonl`에 도구로 기록한다. 로컬 recorded, 실제 전송 sent, 관찰한 수신 received를 구분하고 답변·수신 확인은 원래 이벤트 ID와 연결한다. 읽기 전용 역할은 메인이 기록한다.
- 작업 결과 메시지는 요약, 파일 증거는 상세 기록에 사용한다. 런타임이 제공하지 않는 토큰 수·진행률·완료 이벤트를 추정하지 않는다.

상세 작업/결과 스키마는 [오케스트레이터 템플릿](orchestrator-template.md), 실제 명령과 수명·통신 절차는 [실행 가이드](runtime-guide.md)를 따른다.
