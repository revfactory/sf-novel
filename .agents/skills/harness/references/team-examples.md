# Codex 팀 구성 예시

Phase 2에서 패턴을 실제 도메인에 적용하거나 Phase 5에서 작업 배분을 구체화할 때 읽는다. 아래 역할은 설계 예이며 모두 기본 제공되는 이름은 아니다. 실제 제공 역할과 프로젝트 TOML을 확인한다.

## 1. 리서치: 팬아웃/팬인

메인이 질문·범위·평가 시점·최종 보고서 구조를 확정한다. 조사자 2~3명은 서로 다른 출처 범위를 맡고 메인은 자료 통합 기준을 준비한다.

| 담당 | 독립 책임 | 산출물 |
| --- | --- | --- |
| 조사자 A | 공식 문서와 원자료 | 자기 작업 디렉토리의 주장·출처·날짜 목록 |
| 조사자 B | 배경과 비교 대상 | 자기 작업 디렉토리의 비교 근거 |
| 조사자 C, 필요할 때 | 사용자 반응이나 현장 사례 | 근거와 표본의 한계를 구분한 결과 |
| 메인 | 중복 제거, 상충 판단, 최종 보고 | 사용자가 지정한 보고서 |

웹 도구가 있어야 온라인 조사를 수행할 수 있다. 읽기 전용 파일 시스템 설정과 웹 도구 접근은 별도 조건이다. 도구가 없으면 제공 자료만 분석하고 최신 정보를 확인했다고 주장하지 않는다.

조사자끼리 상충을 발견하면 근거를 공유할 수 있지만 최종 보고서는 메인만 수정한다. 출처가 다른 주장을 단순 투표로 결정하지 않고 날짜·원자료·측정 방법을 비교한다.

## 2. SF 소설: 파이프라인 + 팬아웃

원본의 세계관·인물·플롯 병렬 작업은 공통 전제를 먼저 정해야 한다.

1. 메인이 장르, 중심 갈등, 시점, 분량과 고정 설정을 확정한다.
2. 세계관과 인물 초안을 서로 다른 파일로 병렬 작성한다. 변경 제안은 메인에게 반환한다.
3. 메인이 모순을 조정하고 확정된 설정을 제공한다. 플롯 작성자는 그 결과로 구성한다.
4. 집필자가 초안을 작성한다. 이후 과학 검토와 연속성 검토를 병렬 수행한다.
5. 집필자가 배정된 본문만 수정하고 메인이 최종 연결과 요구사항을 확인한다.

역할 여섯 개를 동시에 띄울 필요는 없다. 장기 집필에서 반복되는 역할만 TOML로 보관하고 짧은 검토는 기본 역할을 재사용한다.

커스텀 역할 예: `.codex/agents/worldbuilder.toml`

```toml
name = "worldbuilder"
description = "소설의 물리·사회·기술 설정을 일관된 세계관으로 정리한다."
sandbox_mode = "workspace-write"
developer_instructions = """
메인이 정한 장르와 고정 설정을 읽고 배정된 세계관 문서만 작성한다.
당신은 혼자 작업하지 않는다. 다른 작업자의 변경을 되돌리지 말고 현재 자료에 맞춘다.
인물·플롯을 직접 변경하지 않고 영향과 대안을 메인에게 제안한다.
사실과 창작 가정을 구분하고 이야기와 관련 없는 설정을 과도하게 늘리지 않는다.
이전 산출물과 피드백이 있으면 영향받은 설정만 보완한다.
추가 에이전트를 만들지 않는다. 상태, 산출물, 일관성 검토 근거, 남은 모순을 반환한다.
"""
```

## 3. 웹툰: 생성-검증

메인이 패널 목록과 캐릭터 기준을 정한다. 생성자는 배정된 이미지 파일을 만들고 검토자는 실제 이미지를 확인한다. 이미지 도구가 없으면 생성·편집을 실행했다고 보고하지 않는다.

검토자는 패널별 `PASS`, `FIX`, `REDO`와 근거를 반환한다. `FIX`는 부분 수정, `REDO`는 재생성이 필요한 상태다. 메인은 문제 패널만 생성자에게 다시 배정하고 기본 최대 2회 검토한다. 반복 한도 후에도 문제가 있는 패널은 그대로 실패로 남긴다.

이미지를 보지 못하면 검토 결과는 `not_run`이며, 로딩 실패를 시각적 품질 불합격과 혼동하지 않는다. 결과 파일과 리뷰를 분리해 생성자와 검토자가 같은 파일을 수정하지 않게 한다.

## 4. 코드 리뷰: 전문가 풀 + 팬아웃

변경 범위에 맞춰 보안·성능·회귀 위험 중 필요한 관점 2~3개를 선택한다. 모두 같은 diff를 읽을 수 있으므로 읽기 소유권은 겹쳐도 된다. 각 리뷰어에게 다른 질문을 주어 동일한 전면 리뷰를 중복하지 않는다.

| 검토 작업 | 구체적인 질문 예 |
| --- | --- |
| 보안 | 인증 컨텍스트가 새 API의 모든 경로에 전달되는가? |
| 성능 | 새 반복 조회가 입력 수에 따라 쿼리 수를 늘리는가? |
| 회귀 | 기존 호출자가 바뀐 응답 형식을 그대로 사용하는가? |

`harness_reviewer`를 필요한 관점별로 호출할 수 있다. 별도의 역할 파일을 매번 만들 필요는 없다. 리뷰어는 파일을 수정하지 않고 파일·행·재현 근거를 반환한다. 메인이 중복 결함을 묶고 우선순위를 정한다. 실행 검증이 필요하면 QA 작업을 별도 배정한다.

## 5. 코드 마이그레이션: 감독자

메인이 파일 목록과 import·공용 타입의 의존성을 파악하고 공통 계약을 먼저 정한다. 독립적인 파일 묶음을 워커 2~3명에게 배정한다.

| 소유자 | 쓰기 범위 |
| --- | --- |
| 메인 | 공용 타입·설정, lockfile, `AGENTS.md`, 작업 장부, 최종 통합 |
| 워커 A | 모듈 A 파일과 자기 작업 디렉토리 |
| 워커 B | 모듈 B 파일과 자기 작업 디렉토리 |
| QA | 완료된 모듈의 검사 로그·캐시·자기 작업 산출물 |

작업 하나가 끝나면 메인이 결과와 범위를 확인하고 실제 에이전트 유휴 상태를 확인한다. 관련 후속 묶음은 변경된 입력·결정·스킬을 포함한 최신 패킷으로 같은 워커에 배정한다. 새 공용 변경이 필요하면 메인이 변경 후 소비자에게 알린다. 워커는 다음 작업을 제안할 수 있지만 장부를 수정하거나 범위를 스스로 확장하지 않는다.

모듈마다 경계면 QA를 수행하고 통합 후 프로젝트의 관련 검사 명령을 실행한다. 필수 모듈이 실패하면 누락한 채 전체 마이그레이션 완료를 선언하지 않는다.

## 6. 풀스택: 계층을 평탄화

설계에서는 프론트엔드 → UI·상태, 백엔드 → API·저장소처럼 계층적으로 생각할 수 있다. 실행은 메인이 모든 작업의 의존성을 보고 제한된 슬롯에 배정한다.

```text
메인: API 계약과 공용 타입 확정
  ├─ API 구현 작업
  ├─ 계약 기반 UI 구현 작업
  └─ 테스트 환경 조사 작업
메인: 구현 결과 확인 → 통합 QA 배정 → 수정·재검증
```

하위 팀장을 추가로 띄워 반복 위임하기보다 `harness_architect`에게 작업 그래프 제안을 받고 메인이 실제 배정을 수행한다. 순환 대기와 슬롯 고갈을 피할 수 있다. UI가 실제 API 결과에 의존하는 부분은 API가 준비될 때까지 기다리고, 독립 레이아웃·계약 기반 작업만 먼저 진행한다.

## 공통 마무리

모든 예시는 [작업·결과 계약](orchestrator-template.md)을 사용한다. 메인은 파일 증거와 검사 결과를 확인하고 실행 요약을 기록한다. 후속 요청은 새 실행 ID로 이전 결과를 연결하며 영향을 받는 작업만 다시 수행한다. 사용자에게 변경 결과와 실제 검증 범위, 남은 제한을 간결히 보고한다.

## 공통 컨텍스트와 통신

각 팀의 메인은 실제 동료 ID·담당 경계 목록과 최신 input.md를 제공한다. 작업자는 다른 역할에 영향을 주는 발견을 먼저 알리고, 필요한 사실을 구체적으로 질문하고 답한다. 계약 제안은 메인에게 전달하고 메인이 확정한 결정만 소비한다. 제품 수정은 워커가 맡고 QA는 재검증한다.

중요한 메시지는 쓰기 가능한 역할이 communication.py로 먼저 기록한 뒤 실제 네이티브 도구로 전달한다. 읽기 전용 조사·리뷰는 메인이 기록·전달한다. 답변·수신 확인은 원래 이벤트 ID와 연결한다. 기록이 메시지를 자동 전달하지 않으며 반복적인 생존 보고는 필요하지 않다. 실제 CLI와 부분 재실행 절차는 [실행 가이드](runtime-guide.md)를 따른다.
