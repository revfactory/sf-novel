# 스킬 테스트와 반복 개선

Phase 6에서 구조·동작·협업을 검증하고 Phase 7에서 회귀를 확인할 때 읽는다. 정적 검증, 실제 작업 실행, 스킬 자동 선택은 서로 다른 검증이다.

## 검증 수준

| 수준 | 확인 대상 | 증명하지 못하는 것 |
| --- | --- | --- |
| 정적 검사 | TOML·frontmatter·참조·작업 그래프·소유권 | 실제 에이전트가 작업에 성공했는지 |
| 실행 검사 | 실제 도구 호출과 산출물, 테스트 명령 결과 | 모든 사용자 표현에서 자동 선택되는지 |
| 트리거 평가 | 스킬을 써야 할 요청과 인접 요청의 선택 | 산출물의 기능 정확성 |
| 통합 QA | 생산자·소비자 연결과 최종 동작 | 검증하지 않은 환경의 동작 |

대상 프로젝트 루트에서 번들 검증기를 실행한다.

```bash
python3 .agents/skills/harness/scripts/validate.py --project .
```

설치·구조 검사만 실행했다면 그 범위로 보고한다. 에이전트 실행 도구가 없거나 역할을 현재 세션에서 사용할 수 없다면 실제 멀티 에이전트 검증은 `not_run`으로 남긴다.

## 작은 실제 실행

생성·오케스트레이션 로직이 바뀌었다면 다음 세 사례로 시작한다. 별도 임시 프로젝트 또는 배타적인 작업 디렉토리를 사용하여 기존 사용자 결과를 보존한다.

1. **정상 병렬 작업:** 공통 입력을 두 워커에게 주고 서로 다른 파일을 작성하게 한다. 메인이 한 파일을 통합한 뒤 독립 리뷰 또는 QA가 완료 기준을 확인한다. 실제 호출 ID, 반환 결과, 파일 경로를 기록한다. 입력 지문·결정·스킬 경로가 최신 패킷에 포함되는지 확인한다.
2. **오류 작업:** 필수 입력 누락 또는 알려진 검증 실패를 제공한다. 작업이 `blocked`/`failed`로 보고되고 선행 결과가 없는 소비자가 실행되지 않는지 확인한다. 재시도 한도를 넘겨도 강제 통과하지 않아야 한다.
3. **부분 재실행:** 입력 하나만 수정한다. 새 실행에서 영향받은 작업과 의존 소비자만 갱신하고, 이전 실행 기록과 관계없는 산출물을 보존하는지 확인한다.

이것은 테스트 시나리오이며 그 자체가 통과 결과는 아니다. 에이전트에게 특정 성공 문장을 출력하게 하는 검사보다 실제 파일·계약·의존성의 동작을 확인한다. 짧은 문구 수정처럼 영향이 작은 변경에는 불필요한 에이전트 실행을 추가하지 않는다.

## 테스트 프롬프트

입력·대상·기대 결과를 구체적으로 적는다. 정상 작업 1개, 경계 사례 1개, 필요하면 복합·후속 작업 1개를 선택한다.

예: “이 프로젝트의 프로필 응답이 `{ profile: {...} }`로 바뀌었어. API와 화면 어댑터를 서로 다른 작업으로 나누고, 이름이 비어 있는 경우도 검증해줘.”

평가 기준은 실행 전에 정한다. “파일이 존재한다”에 더해 “API의 래핑을 풀고 빈 이름을 처리한다”, “공용 설정을 워커가 동시에 수정하지 않는다”, “필수 실패가 후속 완료를 막는다”처럼 목적을 확인한다.

## 스킬 유무·버전 비교

품질이나 효율 차이를 확인할 필요가 있을 때만 비교 평가를 추가한다. 새 스킬은 스킬 없는 기준 실행과, 기존 스킬 개선은 수정 전 스냅샷과 비교한다.

- 입력, 완료 기준, 도구 접근, 모델 조건을 같게 한다. 모델을 임의로 고정하지 않고 현재 사용 환경을 기록한다.
- 두 실행의 파일과 캐시를 분리한다. 같은 제품 파일을 동시에 쓰지 않는다.
- 기준 실행이 평가 대상 스킬을 로딩하지 않도록 별도 환경을 사용한다. 현재 환경에서 이를 보장할 수 없다면 “스킬 없는 기준 실행”이라고 주장하지 않는다.
- 필요한 입력만 제공하여 이전 정답이나 상세 이력을 통한 평가 오염을 줄인다.
- 객관적인 요구사항을 먼저 채점하고 문체·설계 품질은 명확한 기준으로 검토한다. 단순 문구 변경마다 대규모 벤치마크를 요구하지 않는다.

## 결과와 근거

검사별 `passed`, `failed`, `not_run`을 기록한다. `not_run`은 생략 사유를 포함하며 통과율에 섞어 성공으로 계산하지 않는다.

```json
{
  "case": "required-input-missing",
  "expectations": [
    {
      "text": "필수 입력이 없을 때 후속 구현을 완료 처리하지 않는다",
      "status": "passed",
      "evidence": "task-01/result.json은 blocked, task-02는 pending"
    },
    {
      "text": "브라우저에서 최종 화면이 동작한다",
      "status": "not_run",
      "evidence": "이 실행에는 브라우저 검증 환경이 없음"
    }
  ]
}
```

위 JSON은 평가 기록의 예이며 번들 도구가 자동 생성한다고 가정하지 않는다. 도구가 제공하는 토큰·시간 수치만 저장한다. 제공하지 않는 값은 생략하거나 미측정으로 표기한다. 실행 시간과 토큰 비용을 추정한 수치로 대체하지 않는다.

## 트리거 검증

스킬 description을 바꿀 때 자동 선택을 기대하는 요청과 선택되면 안 되는 인접 요청을 비교한다. 가벼운 변경은 대표 경계 사례만 검토하고, 트리거 품질이 중요하면 각각 8~10개로 넓힌다.

| 하네스가 필요한 요청 | 인접하지만 자동 생성하면 안 되는 요청 |
| --- | --- |
| “이 저장소에 Codex 하네스를 구성해줘” | “멀티 에이전트가 뭔지 설명해줘” |
| “기존 역할과 스킬 연결을 점검해줘” | “이 문서의 agent 오타를 수정해줘” |
| “하네스에 데이터 변환 역할을 추가해줘” | “변환 함수 한 개만 수정해줘” |
| “이전 하네스 결과에서 QA 단계만 보완해줘” | “하네스라는 제품의 소개문을 다듬어줘” |

description을 읽고 판정하는 수동 검토와 새 세션에서 실제 선택을 관찰하는 평가를 구분한다. 도구나 CLI가 명시적으로 관찰 기능을 제공하지 않으면 추정으로 자동 트리거 성공률을 보고하지 않는다.

## 반복 개선과 종료

문제 → 원인 → 일반적인 지침 수정 → 영향받는 검사 재실행 순서로 진행한다. 반복 코드를 발견하면 검증된 스크립트로 묶는다. 기본 QA 수정 반복은 최대 2회이며 복잡한 작업에 다른 한도가 필요하면 시작 시 기록한다.

완료 기준과 필수 검사가 충족되면 종료한다. 한도 내에 해결하지 못한 필수 실패는 남은 문제로 보고하고 전체 성공을 선언하지 않는다. 사용자의 침묵을 만족·승인·검증 근거로 취급하지 않는다.

평가 산출물은 `.harness/runs/<run-id>/task-<id>/eval-<case>/`에 저장한다. 새 반복마다 하위 디렉토리를 추가하여 이전 결과를 보존하고 최종 보고에서는 실제 수행한 범위만 요약한다.

## 실행 계약 검증

- 필요한 run.py 상태 전이와 validate.py --run ID --complete를 실제 임시 대상에서 확인한다. 산출물·필수 검사 근거·입력 최신성이 빠지면 완료를 주장하지 않는다.
- 같은 에이전트 재사용 전에 갱신된 패킷을 읽는지 확인하고, 부분 재실행에서는 변경된 입력·계약·결과 및 소비 작업이 무효화되는지 확인한다.
- 결과 등록과 실제 세션 유휴·중단·종료를 별도 확인한다. stop_requested 기록만으로 동시 작성자를 재배정하지 않는다.
- 의미 있는 발견·질문·답변·인계를 기록하고 실제 네이티브 메시지 전달 결과를 별도 관찰한다. 상관 ID, recorded/sent/received 구분, 읽기 전용 역할의 메인 대리 기록을 확인한다. 로컬 로그만 있는 사례를 네이티브 전달 통과로 처리하지 않는다.
- 상세 명령은 [실행 가이드](runtime-guide.md)를 따른다. 이 목록은 검증 시나리오이며 실행 결과가 아니다.

## 저장소의 선택적 네이티브 실행 검사

인증된 일반 Codex 클라이언트가 있는 환경에서 이 저장소 루트의 다음 명령을 사용한다. `scripts/live_smoke.py`는 저장소 전용 도구이며 대상 프로젝트에 설치되는 스킬 번들에는 포함되지 않는다.

```bash
python3 scripts/live_smoke.py run --target _workspace/live-tests/NEW_ID
```

새 대상 디렉터리를 지정한다. 제한 시간은 1,200초이며 기본 CI에서 실행하지 않는다. 이 시나리오는 실제 커스텀 워커 2개를 생성하고 alpha 작성 성공·beta 명세 불일치 차단 → 완료 검사 실패 → 명세 수정과 resume → 변경 없는 alpha 결과 재사용·beta 작성 → QA 단언 2개를 검증한다. 도구의 실제 결과와 파일·대화·검사 근거를 보고 통과 여부를 판단한다. 계획된 시나리오나 명령이 존재한다는 이유로 실행 통과를 주장하지 않는다.
