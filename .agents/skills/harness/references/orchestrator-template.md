# Codex 오케스트레이터 템플릿

Phase 5에서 도메인 오케스트레이터를 만들거나 수정할 때 읽는다. 아래 형식은 하네스가 관리하는 작업 계약이다. Codex 도구 API나 내장 태스크 서비스의 스키마가 아니다. 실제 상태·통신 CLI는 [실행 가이드](runtime-guide.md)를 따른다.

## 스킬 골격

```markdown
---
name: domain-orchestrator
description: "{도메인}의 {산출물}을 생성·검증한다. {시작 표현}, 결과 수정·보완·업데이트, 이전 결과 기반 부분 재실행에 사용한다. {인접하지만 제외할 작업}은 해당 전문 스킬을 사용한다."
---

# {도메인} 오케스트레이터

## 목표와 완료 기준
{입력}, {최종 산출물 경로}, {필수 요구사항}, {검증 명령 또는 검토 기준}.

## 역할과 소유권
{역할별 책임}, {독립 쓰기 경로}, {필요한 스킬 경로}.
메인이 작업 장부, 공용 계약·설정, 통합과 완료 판정을 소유한다.

## 실행
1. 기존 지시·산출물·실행 기록을 확인하고 최초/새 입력/부분 재실행을 구분한다.
2. run.py init으로 입력 지문·결정·스킬 경로가 있는 v2 실행을 만든다. 부분 재실행은 resume으로 이전 실행을 연결한다.
3. 실제 도구 스키마와 역할 목록, 사용 가능한 동시 실행 수를 확인한다. 실행 가이드의 네이티브 실행 사전 점검에 따라 첫 대기 자식 하나의 실제 생성 응답·ID를 확인한다. 부모 스레드 오류로 ID 없이 실패하면 추가 생성을 멈추고 순차 대체 절차를 따른다.
4. 성공한 첫 자식을 준비된 작업에 맞는 역할로 등록·재사용한 뒤, 선행 작업이 완료된 독립 작업 2~3개로 넓힌다. 실제 슬롯 한도를 지키며 메인은 별도 통합 작업을 수행한다.
5. 중요한 발견·질문·답변·차단 사유·인계를 기록 후 실제 메시지로 전달한다. 결과를 수집하여 의존성을 풀고 완성된 모듈의 경계면을 즉시 검증한다.
6. 문제를 소유자에게 재배정하고 정해진 횟수 안에서 수정·재검증한다.
7. 메인이 결과 등록, 실제 세션 상태 확인, validate.py --run ID --complete, 최종 통합 검사와 결과 보고를 수행한다.

## 오류와 후속 작업
필수 실패는 완료를 막는다. 선택적 생략은 사유와 영향을 기록한다.
네이티브 도구가 없거나 첫 생성이 부모 스레드 오류로 실패하면 같은 실질 작업을 메인 세션에서 순차 수행한다. 시작되지 않은 네이티브 작업은 pending으로 남기고 메인의 변경·검사는 별도 기록한다. 가짜 ID로 start하거나 네이티브 스모크 테스트를 순차 대체로 통과 처리하지 않는다. 사용자의 기록 선호를 바꾸어 영속 세션을 조용히 시작하지 않는다.
변경된 입력·공용 계약의 영향을 받는 하위 작업을 함께 재실행한다.

## 테스트 시나리오
- 정상: {독립 작업 2개 → 통합 → 검증}.
- 오류: {필수 작업 실패 → 제한된 수정 → 여전히 실패하면 실패 보고}.
- 후속: {부분 수정 → 영향받은 작업만 재실행 → 이전 기록 보존}.
```

템플릿의 중괄호는 대상 프로젝트의 사실로 채운다. 존재하지 않는 명령·역할·산출물 경로를 남기지 않는다.

## 실행 디렉토리와 작업 장부

실행 ID는 충돌하지 않는 값으로 만들고 기존 디렉토리가 있으면 새 값을 선택한다.

```text
.harness/runs/<run-id>/
├── plan.json                 # 메인이 run.py로 갱신, v2 입력·상태
├── agents.json               # 작업 상태와 구분한 에이전트 레지스트리
├── summary.md                # 메인이 결과·변경 이유 기록
├── task-01/
│   ├── input.md              # 메인이 기록한 작업 계약
│   └── result.json           # 워커 반환 결과, 또는 메인이 메시지 기록
└── task-02/
    ├── input.md
    ├── checks.log
    └── result.json
```

읽기 전용 에이전트는 파일을 쓰도록 강요하지 않고 결과·중요 메시지를 반환한다. 메인이 해당 결과와 통신 사건을 기록한다. 워커는 자기 작업 디렉토리와 할당된 제품 파일만 수정하며, 통신 기록은 communication.py로 공유 `_workspace/communications/<run-id>.jsonl`에 추가한다. 공유 장부·로그를 직접 편집하지 않는다.

`run.py init --plan-file`에 전달할 계획 예시다. init이 schema_version 2, project_root, 입력·계약 지문, 작업 초기 상태를 기록한다. 실제 경로로 바꾼 뒤 사용한다:

```json
{
  "run_id": "20260907-120000-example",
  "previous_run_id": null,
  "objective": "프로필 API와 화면을 연결하고 검증한다",
  "tasks": [
    {
      "id": "01",
      "role": "harness_worker",
      "dependencies": [],
      "ownership": ["src/profile/adapter.ts"],
      "inputs": ["docs/profile-contract.md"],
      "context": {"decisions": ["확정된 profile 응답 키를 유지한다"], "skill_paths": []},
      "acceptance": ["확정된 응답 계약에 맞게 프로필을 변환한다"],
      "status": "pending",
      "attempts": 0,
      "required": true
    },
    {
      "id": "02",
      "role": "harness_qa",
      "dependencies": ["01"],
      "ownership": [".harness/runs/20260907-120000-example/task-02/"],
      "inputs": ["docs/profile-contract.md"],
      "context": {"decisions": ["QA는 제품을 수정하지 않고 실제 경계를 검증한다"], "skill_paths": []},
      "acceptance": ["응답 생산자와 소비자의 런타임 데이터 형식이 일치한다"],
      "status": "pending",
      "attempts": 0,
      "required": true
    }
  ]
}
```

경로는 프로젝트 루트 기준 상대 경로이며 `..`로 프로젝트 밖을 소유하지 않는다. `dependencies`는 작업 ID 목록이다. 허용 상태는 `pending`, `running`, `completed`, `blocked`, `failed`, `skipped`이며 `skipped`는 선택적 작업에만 사용한다. 메인은 실제 호출 ID를 레지스트리에 연결한다. inputs에는 작업 중 바꾸지 않는 계약·참조만 두고 수정 대상 ownership과 겹치지 않게 한다. 선행 결과·산출물은 dependencies를 통해 start 시점에 경로·지문과 함께 전달된다.

## 위임 프롬프트 계약

런타임의 실제 spawn 도구에 아래 내용을 작업 지시로 전달한다. 이 텍스트의 필드를 도구의 인자로 그대로 보내지 않는다.

```text
실행/작업 ID: 실제 run-id / 01
프로젝트 루트: 실제 절대 경로
최신 패킷: .harness/runs/<run-id>/task-01/input.md
목표: 프로필 응답을 화면 모델로 변환한다.
불변 입력: docs/profile-contract.md 및 패킷에 기록된 지문
코드 읽기 범위: src/api/profile.ts
결정/스킬: 패킷의 context.decisions와 context.skill_paths를 읽는다.
선행 결과: 메인이 확정한 선행 결과·산출물과 패킷의 지문
소유권: src/profile/adapter.ts 및 지정된 task-01 산출물 경로만 수정
공유 작업: 다른 작업자도 있다. 그들의 변경을 되돌리지 말고 현재 코드에 맞춘다.
메인 소유: plan.json, 공용 타입·설정, AGENTS.md, 최종 통합
절차: 지정된 스킬이 있으면 해당 SKILL.md와 필요한 참조만 읽는다.
검증: 프로젝트에서 실제 확인한 관련 테스트 명령을 실행한다.
완료 기준: 응답 계약 일치, 관련 테스트 성공, 변경 파일과 근거 반환
오류: 필수 입력 누락·소유권 충돌은 메인에게 알려 관련 작업만 멈춘다.
동료 목록: 실제 에이전트 ID, 역할, 담당 경계, 메인 ID
협업: 필요한 사실은 담당 동료에게 구체적으로 질문하고 신속히 답한다.
발견·차단·준비·이정표·인계는 먼저 전달하되 계약과 소유권은 메인이 확정한다.
통신: 쓰기 가능하면 사건 기록 → 실제 네이티브 전송 → 전송 결과 기록;
읽기 전용이면 메인에게 기록을 요청한다. 답변·수신 확인은 원래 이벤트 ID와 연결한다.
추가 에이전트를 만들지 말고 필요한 분할은 메인에게 제안한다.
후속: 최신 input.md와 변경된 계약·스킬을 다시 읽고 영향받는 부분만 수정한다.
중단 요청: 쓰기를 멈추고 마지막 변경·실행 중 검사를 보고하여 소유권 인계를 확인한다.
반환: run_id, task_id, status, summary, artifacts, checks, issues
```

## 결과 계약

```json
{
  "run_id": "20260907-120000-example",
  "task_id": "01",
  "status": "completed",
  "summary": "프로필 응답 변환을 구현했다",
  "artifacts": ["src/profile/adapter.ts"],
  "checks": [
    {
      "name": "프로필 변환 테스트",
      "status": "passed",
      "required": true,
      "command": "프로젝트에서 실제 실행한 명령을 기록",
      "evidence": "실행 로그 경로 또는 구체적인 출력 요약"
    }
  ],
  "issues": []
}
```

작업 결과 상태는 `completed`, `blocked`, `failed` 중 하나다. 검사 상태는 `passed`, `failed`, `not_run`이다. 실행 명령이 없는 수동 검토는 `command`를 생략하고 확인한 파일·행·결과를 근거에 쓴다. 검사마다 required 여부를 적는다. completed에는 최소 한 개의 필수 passed 검사와 모든 필수 검사의 실제 근거가 필요하다. 예시 문자열을 실제 결과로 제출하지 않는다.

메인은 자식의 자기 평가만으로 완료 처리하지 않는다. run.py result로 결과를 등록하고 산출물 존재, 수정 범위, 완료 기준, 검사 근거와 지문의 최신성을 확인한다. 읽기 전용 리뷰의 `artifacts`는 빈 목록이어도 되며 메시지 근거를 기록한다. 승인된 artifacts는 이후 단계가 변경하지 않는 인계 출력이다. 단계별 별도 출력 경로를 사용하고 변경된 결과와 소비자는 재검증한다. 개별 파일 또는 전용 outputs/를 반환하며 result.json·plan.json·agents.json이 포함되는 작업·실행 디렉터리 전체를 artifacts에 넣지 않는다.

## 스케줄링과 통신

1. `pending`이고 모든 선행 작업이 `completed`인 작업을 고른다. 선택적 선행 작업 생략이 허용되는 경우에는 계약을 갱신한 뒤 실행한다.
2. 실행 중인 작업과 소유 경로가 겹치지 않는지 확인한다. 첫 대기 자식 하나의 실제 ID가 반환되는지 확인한 뒤 그 자식을 첫 작업에 재사용한다. 새 자식은 본 작업 없이 대기 지시로 생성하고 실제 ID를 run.py start로 등록해 최신 패킷을 준비한 뒤 실제 후속 도구로 배정한다. 생성·등록에 실패하면 작업을 전달하지 않는다. 첫 생성이 성공하고 동시 실행 슬롯과 메인의 독립 작업이 모두 있을 때 추가 자식을 생성해 병렬화한다.
3. 실제 동료 ID·책임 목록을 전달한다. 자식은 영향을 주는 발견을 먼저 알리고 필요한 사실을 질문하며, 답변·차단·인계를 근거와 함께 전달한다. 메인도 계약 결정을 관련 소비자에게 전파한다.
4. 중요한 발신은 communication.py로 기록한 뒤 실제 도구로 전송한다. 전송 결과와 수신 답변을 이벤트 ID로 연결한다. 읽기 전용 역할의 기록과 미지원 동료 통신은 메인이 대신한다. 기록이 전송을 대신하지 않는다.
5. 완료 결과를 등록한 뒤에도 네이티브 세션 상태를 별도 확인한다. 중단 요청만으로 다른 작성자에게 소유권을 넘기지 않는다. 실제 유휴·중단 확인을 레지스트리에 기록한다.
6. 관련 후속 작업은 최신 패킷과 함께 기존 에이전트에 배정한다. 실행을 재개하는 실제 도구를 사용한다. 불필요한 세션은 실제 종료 도구로 정리한 뒤 closed를 기록하며, 결과 수신·기다림·로컬 상태 변경이 슬롯 반환을 보장한다고 가정하지 않는다.

병렬 테스트가 동일한 빌드 디렉토리·데이터베이스·캐시를 변경하면 순차 실행하거나 격리된 출력 경로를 지정한다. 코드 파일 소유권이 다르더라도 실행 부작용은 충돌할 수 있다.

## 오류 처리

| 상황 | 대응 |
| --- | --- |
| 일시적인 도구 실패 | 원인 확인 후 기본 1회 추가 시도. 아래 부모 스레드 오류에는 역할별 재시도를 적용하지 않음 |
| `collab spawn failed: no thread with id`로 자식 ID 없이 실패 | 추가 생성 중단, 원문 오류·알려진 모드와 버전 기록. 가짜 ID 등록 없이 기존 메인 세션의 순차 대체 절차 적용 |
| 작업 범위·입력 불충분 | 가능한 독립 작업은 계속하고 필요한 사실을 메인에게 보고 |
| 소유권 충돌 | 관련 쓰기를 멈추고 메인이 기존 변경을 보존하며 재배분 |
| 상충되는 분석 | 출처·재현 근거를 비교하고 메인이 결론 또는 남은 불확실성 기록 |
| QA 실패 | 담당 소유자가 수정, 기본 최대 2회 수정·재검증 |
| 필수 작업이 여전히 실패 | 작업을 실패/차단 상태로 유지하고 전체 완료를 주장하지 않음 |
| 선택 작업 생략 | 메인이 생략 사유와 최종 결과에 미치는 영향 기록 |
| 실제 서브에이전트 도구 없음 | 메인이 같은 실질 작업을 순차 수행하고 별도 근거 기록. 네이티브 pending 작업은 완료로 제출하지 않으며 병렬 실행은 미검증으로 보고 |
| 네이티브 전용 스모크의 생성 실패 | 생성 검사는 실패, 후속 미실행 검사는 미실행으로 보고. 순차 대체로 통과 처리하지 않음 |

## 부분 재실행과 drift

이전 기록을 읽고 변경 입력 → 산출물 → 소비자 순서로 영향을 추적한다. 독립 산출물은 재사용하고 변경된 공용 계약의 소비자는 다시 검증한다. `run.py resume`으로 새 실행을 연결하고 입력·계약·결과 변경과 하위 의존성의 무효화 여부를 확인한다. 과거 기록을 덮어쓰지 않는다. 사용자에게 표시할 최종 파일의 수정은 원래 요청 범위에 따른다.

역할명·스킬명·경로를 바꾸면 오케스트레이터 호출부, 해당 스킬 참조, `AGENTS.md` 관리 블록을 함께 갱신한다. 매 실행 기록을 `AGENTS.md`에 복사하지 않는다.
