# Codex 스킬 작성 가이드

Phase 4에서 새 스킬을 만들거나 기존 스킬을 일반화할 때 읽는다. 스킬은 재사용할 작업 절차이며, 역할 정의와 실행 기록을 대신하지 않는다.

## 범위와 재사용

먼저 기존 스킬의 description을 읽고 요청과 겹치는지 판단한다. 요구를 충분히 포함하면 재사용하고, 책임 범위 안의 작은 확장은 기존 스킬을 수정한다. 의도적인 도메인 차이가 있거나 별도의 반복 절차일 때 새 스킬을 생성한다.

단순 작업마다 스킬을 만들지 않는다. 동일한 절차·검증·참조가 반복되어 다음 실행의 품질이 좋아지는지가 기준이다. 기존 스킬을 일반화하면 호출하는 역할과 오케스트레이터의 동작이 유지되는지 확인한다.

## 디렉토리와 메타데이터

```text
.agents/skills/profile-migration/
├── SKILL.md
├── agents/openai.yaml       # 선택: UI 메타데이터
├── references/              # 필요한 경우에만 읽는 상세 지식
├── scripts/                 # 반복되는 결정적 작업
└── assets/                  # 최종 산출물에 쓰는 템플릿 등
```

폴더와 `name`은 같은 소문자 하이픈 이름을 사용한다. 프로젝트 범위가 기본이며 개인 설치는 사용자가 요청한 경우에만 `~/.agents/skills/`에 한다.

```yaml
---
name: profile-migration
description: "프로필 API의 응답 계약과 소비 코드를 함께 마이그레이션한다. 프로필 응답 형식 변경, 필드 이름 동기화, 기존 마이그레이션 보완·부분 재실행에 사용한다. 프로필 화면의 색상·간격 수정은 해당 UI 작업 절차를 따른다."
---
```

description은 발견·선택을 돕는 핵심 메타데이터다. 사용자는 `$profile-migration`으로 명시적으로 호출할 수도 있다. 무조건적인 키워드 점유보다 작업과 경계를 분명히 쓴다.

`agents/openai.yaml`은 에이전트 역할 TOML과 다른 UI 설정이다. 사용한다면 모든 문자열을 따옴표로 감싸고 `default_prompt`에 `$skill-name`을 포함한다. `short_description`은 25~64자 정도로 작성한다. 없는 아이콘·의존 도구를 선언하지 않는다.

## 본문 골격

```markdown
# 프로필 응답 마이그레이션

## 입력과 완료 기준
기존 응답, 목표 계약, 소비자 목록과 관련 검증 명령을 확인한다.

## 절차
1. 기존 생산자와 소비자를 함께 읽고 차이와 영향 범위를 정리한다.
2. 메인과 공통 계약·쓰기 소유권을 확인한다.
3. 소유한 변환 코드를 수정하고 호출부와 런타임 응답을 비교한다.
4. 실제 관련 테스트를 실행하고 변경 파일·결과·남은 문제를 반환한다.

## 상세 참조
페이지네이션 응답을 바꾸면 `references/pagination.md`를 읽는다.
```

작업을 수행하는 순서와 종료 조건을 명령형으로 쓴다. 실수 가능성이 큰 제약에는 이유를 붙인다. 예를 들어 “제네릭 타입 선언은 런타임 응답을 검증하지 않으므로 생산자와 소비자를 함께 비교한다”는 지침이 단순한 타입 검사 지시보다 유용하다.

## 단계적 정보 공개

| 계층 | 넣을 내용 | 읽는 시점 |
| --- | --- | --- |
| `name`, `description` | 역할과 사용 경계 | 스킬 선택 |
| `SKILL.md` 본문 | 핵심 절차와 참조 선택 기준 | 스킬 사용 시 |
| `references/` | 특정 프레임워크·형식·상세 계약 | 관련 조건이 발생했을 때 |
| `scripts/` | 검증된 반복 코드 | 필요한 작업을 실행할 때 |

본문을 500줄 이내로 유지한다. 길어진 설명은 참조로 옮기고 본문에서 읽는 조건을 연결한다. 300줄이 넘는 참조에는 목차를 둔다. 여러 도메인이 있으면 관련 문서만 선택하도록 분리한다.

스킬 본문을 에이전트 TOML에 통째로 복사하지 않는다. 위임 시 스킬의 절대 경로 또는 확실한 프로젝트 상대 경로를 알려주고 필요한 본문을 읽게 한다. 자식이 부모의 모든 스킬 본문을 물려받는다고 가정하지 않는다. 필요한 경로는 작업의 context.skill_paths에 넣어 지문과 함께 전달하고, 후속 작업에서는 갱신된 input.md와 변경된 스킬을 다시 읽게 한다.

## 스크립트와 산출물 계약

매 실행에서 같은 파서·변환기·검증 코드를 다시 작성한다면 번들링한다. 반복성이 없는 간단한 문서 편집은 지시만으로 충분하다. 추가한 스크립트는 대표 정상 입력과 의미 있는 실패 입력으로 실행해 확인한다. 의존성은 실제 사용하는 것만 명시한다.

CLI 사용법에는 실행 위치, 입력, 출력, 덮어쓰기 동작을 명시한다. 번들 스크립트 경로는 사용자의 현재 디렉토리와 다를 수 있으므로 확인 후 실행한다. 존재하지 않는 도구·플래그를 문서에 예시로 만들지 않는다.

에이전트 사이에 전달할 JSON·표·파일 형식이 중요하면 최소 필드와 실패 표현을 정한다. 하네스 작업 결과는 [오케스트레이터의 결과 계약](orchestrator-template.md)을 재사용한다. 도메인별 추가 자료는 작업 디렉토리에 두고 공용 장부는 메인이 관리한다.

## 개선 규칙

- “Q4 매출 열만 변환” 같은 테스트 전용 예외보다 대상 데이터의 의미와 변환 실패 처리 원칙을 적는다.
- 같은 검증이 계속 빠진다면 실행 순서에 넣는다. 중복 설명이나 실제로 사용하지 않는 참조는 제거한다.
- 개별 실행 결과, 채점 로그, 반복 이력은 `.harness/runs/`에 둔다. 중요한 협업 사건은 communication.py를 통해 `_workspace/communications/`에 기록한다. 스킬 안에 실행별 로그나 보조 README를 쌓지 않는다.
- 트리거 경계를 바꿨다면 인접 스킬의 description과 비교한다. 이름·경로를 바꾸면 모든 호출부를 함께 갱신한다.

검증 범위와 실제 실행 방법은 [스킬 테스트 가이드](skill-testing-guide.md)를 따른다.

작업·세션 상태, 적극적인 동료 질문·답변, 기록과 실제 전송의 구분은 [실행 가이드](runtime-guide.md)를 참조한다. 도메인 스킬에도 결과 완료와 네이티브 에이전트 중단을 혼동하지 않는 절차를 적용한다.
